## 1. 一句话定位与核心价值

本项目是一个**基于知识图谱的中医智能问答系统**，官方名"本草通 2.0"。它的核心链路是：

```
原始数据 → 结构化本体 → Neo4j 图谱 → 安全消毒 → 问答/API/前端
```

区别于传统"LLM 直接背答案"，它的价值在于：

- **知识可溯源**：每个实体、每条边都带 `Provenance`（出处置信度），回答不是凭空编造。
- **安全优先**：三层防线确保含毒性成分的方剂/药材**绝不给剂量**，只输出警示并引导就医。
- **辨证可解释**：辨证结果带"命中主症/次症 + 评分"，用户能看到推理依据。

## 2. 术语表：先建立共同语言

> 约定：术语保留原文（便于对照代码），括号内为中文解释。

### 2.1 知识图谱与图数据库

| 术语 | 中文解释 |
|---|---|
| **Knowledge Graph（知识图谱）** | 用"节点 + 边"组织知识的结构化数据。节点是实体，边是实体间的关系。 |
| **Entity（实体）/ Node（节点）** | 图谱里的一个对象，如一味药「黄芪」、一个证候「气虚证」。 |
| **Relation（关系）/ Edge（边）** | 实体之间的连接，如「四逆汤 → 附子」的"组成"关系。 |
| **Property（属性）** | 挂在节点或边上的字段，如「附子」的 `toxicity=有毒`。 |
| **Ontology（本体）** | 预先约定好的"数据结构规范"：有哪些实体类型、每种实体有哪些字段、哪些关系合法。图谱的"宪法"。 |
| **Neo4j** | 一款图数据库（Graph Database），专为存储/查询"节点+边"设计，查询语言叫 Cypher。 |

### 2.2 数据与序列化

| 术语 | 中文解释 |
|---|---|
| **JSON** | 一种键值对文本格式，如 `{"name": "黄芪"}`，跨语言通用。 |
| **JSONL** | "JSON Lines" 的缩写，每行一个独立 JSON 对象，适合流式读写大文件。项目里 `data/parsed/*.jsonl` 即此格式。 |
| **Envelope（信封）** | 项目自定的中间数据包格式，统一包装 `kind`（entity 还是 relation）、`label`/`type`、`record`（真正数据）。管线各阶段之间传递的就是 envelope。 |
| **Pydantic** | Python 数据校验库。用类定义字段类型，实例化时自动校验，字段不合法即报错。项目的 12 实体/20 关系都用它建模。 |
| **Schema（模式）** | 数据结构的书面定义，规定有哪些字段、什么类型、是否必填。 |
| **CSV** | 逗号分隔的表格文本，`data/curated/*.csv` 的人工整理表即此格式。 |

### 2.3 图数据库操作

| 术语 | 中文解释 |
|---|---|
| **Cypher** | Neo4j 的查询语言，类似关系数据库里的 SQL。 |
| **MERGE** | Cypher 的"存在则更新、不存在则创建"语义，天然幂等（重复执行结果不变）。项目入库全用 MERGE。 |
| **MATCH** | Cypher 的"查询/匹配"子句，类似 SQL 的 SELECT。 |
| **UNIQUE 约束（唯一约束）** | 保证某字段值全局唯一。12 类实体的 `name` 都建了唯一约束，防止重名节点。 |
| **索引（Index）** | 加速查询的数据结构。项目建了全文索引（name）支持模糊检索。 |
| **幂等（Idempotent）** | 同一操作执行多次，结果与执行一次相同。入库依赖 MERGE 实现幂等，重跑不影响计数。 |

### 2.4 向量与检索

| 术语 | 中文解释 |
|---|---|
| **Embedding（向量嵌入）** | 把一段文本编码成一串数字（向量），语义相近的文本向量也相近。如「失眠」和「睡不着」向量很近。 |
| **bge-m3** | 北京智源（BAAI）开源的多语种嵌入模型，本项目用它生成 1024 维向量。 |
| **HNSW** | "分层可导航小世界图"，一种近似最近邻检索算法，查询快、精度高、支持增量插入。Neo4j 内置支持。 |
| **余弦相似度（Cosine Similarity）** | 衡量两个向量方向的接近程度（0~1），用于判断两个名称是否指同一实体。 |
| **召回（Recall）** | 从大量候选中"粗筛"出可能相关的一小批，交给下一步精判。 |

### 2.5 大模型与智能体

| 术语 | 中文解释 |
|---|---|
| **LLM（大语言模型）** | 如 GPT/Qwen 等，能理解并生成自然语言。 |
| **Agent（智能体）** | 能自主"决策→调用工具→看结果→再决策"的循环体，而非一次性输出。 |
| **Tool Loop（工具循环）** | Agent 的核心机制：LLM 输出"调哪个工具"→ 工具执行 → 结果回填 → LLM 再决策，循环直到给出最终答案。 |
| **Structured Output（结构化输出）** | 让 LLM 按预设字段结构（而非自由文本）输出，便于程序解析。 |
| **Prompt（提示词）** | 喂给 LLM 的指令文本。 |
| **StructuredLLM / ChatLLM（协议）** | 项目中定义的 LLM 抽象接口（Python Protocol），实现可替换，测试注入假实现。 |
| **Fallback（降级）** | 主路径不可用时的备用路径。如 LLM 未配置 → 降级为规则 Agent。 |

### 2.6 中医领域术语

| 术语 | 中文解释 |
|---|---|
| **性味归经** | 中药学的核心描述维度："性"（寒热温凉）、"味"（酸苦甘辛咸等）、"归经"（作用于哪些脏腑经络）。 |
| **毒性分级** | 项目分四级：无毒 / 小毒 / 有毒 / 大毒。其中"有毒、大毒"触发剂量隐藏。 |
| **君臣佐使** | 方剂中每味药的配伍角色：君（主药）、臣（辅药）、佐（抑制副作用/协助）、使（引经/调和）。 |
| **十八反 / 十九畏** | 两套配伍禁忌歌诀，规定某些药物组合"相反/相畏"，不可同用（如甘草反甘遂）。 |
| **妊娠禁忌** | 孕妇禁/忌/慎用的药物，分"禁用、忌用、慎用"三级。 |
| **证候（Pattern）** | 中医"辨证"的对象，是对疾病某阶段病理的概括（如"气虚证""阴虚证"）。 |
| **主症 / 次症** | 一个证候的核心症状（主症，诊断权重高）与次要症状（次症，权重低）。用于辨证加权。 |
| **炮制 / 炮制品** | 对药材加工以减毒增效（如生附子 → 制附片/炮附片）。**生品 vs 炮制品毒性与监管完全不同**，是安全防线的分界。 |
| **经方 / 时方 / 中成药** | 方剂三种类型：经方（经典古方）、时方（后世方）、中成药（成品制剂）。 |

## 3. 分层架构总览

项目为标准的分层结构，代码位于 `backend/src/tcm_kg/`：

```
tcm_kg/
├── ontology/   本体层：枚举、实体、关系模型（数据结构的"宪法"）
├── pipeline/   数据管线层：下载、解析、对齐、入库、嵌入、LLM、抽取
├── graphdb/    图数据库仓储层：Neo4j 读写封装
├── agent/      Agent 层：安全消毒器、六工具、Agent 循环
├── api/        API 层：FastAPI 服务端点
├── core/       横切层：配置、日志、链路追踪
└── cli.py      命令入口：tcm 子命令
```

**依赖方向**（上层依赖下层，下层不反向依赖）：

```
core（零业务依赖）
  ↑
ontology（只依赖 core 吗？不，只依赖 Pydantic）
  ↑
graphdb / pipeline（依赖 ontology 的模型）
  ↑
agent（依赖 ontology 枚举 + graphdb 协议）
  ↑
api（依赖 agent + graphdb）
```

关键设计：**Agent 层不直接依赖 Neo4jRepo 具体类**，而是依赖一个最小 `GraphRepo` Protocol（只声明一个 `run` 方法）。这样测试时可注入 `FakeRepo`（内存假图），实现单元测试与真实图库解耦。

## 4. 本体层：12 实体 + 20 关系 + 枚举

本体是整个系统的"单一事实源"（Single Source of Truth）：所有下游的数据结构都以这里为准。文件在 `ontology/`。

### 4.1 枚举（enums.py）

枚举把术语约束成**有限的可选值**，避免拼写错误与脏数据。核心几个：

#### Toxicity —— 毒性分级（安全核心）

```python
class Toxicity(StrEnum):
    NONE = "无毒"
    SLIGHT = "小毒"
    TOXIC = "有毒"
    HIGHLY_TOXIC = "大毒"

    @property
    def rank(self) -> int:
        # 严重度序：无毒=0 < 小毒=1 < 有毒=2 < 大毒=3
        return {"无毒": 0, "小毒": 1, "有毒": 2, "大毒": 3}[self.value]

    @property
    def requires_dose_masking(self) -> bool:
        # 剂量隐藏判定：毒性 ∈ {有毒, 大毒} → True
        return self.rank >= Toxicity.TOXIC.rank
```

**讲解**：给枚举挂 `rank`（严重度序）和 `requires_dose_masking`（是否需隐藏剂量）两个属性，把"毒性→处理规则"的映射写进数据本身，而不是散落在各处的 if 判断里。这是"把业务规则收进模型"的典型做法。剂量隐藏矩阵（§7.4）在 `sanitizer.py` 里通过 `requires_mask` 复用这一语义。

| `Meridian` | 肺/大肠/胃/脾/心/小肠/膀胱/肾/心包/三焦/胆/肝 | 归经 |

| `FormulaRole` | 君/臣/佐/使 | 配伍角色 |

### 4.2 实体（entities.py）—— 12 类节点

`EntityType` 枚举总表定义 12 类，对应图谱中的 12 个节点标签：

| 实体 | Label | 说明 |
|---|---|---|
| 中药（饮片级） | `Herb` | 规范名以 2020 药典为准 |
| 方剂 | `Formula` | ≥2 味药组成的处方单元 |
| 中医疾病 | `DiseaseTCM` | GB/T 15657 A 码标准名 |
| 证候 | `Pattern` | 辨证论治的"证" |
| 中医症状 | `SymptomTCM` | 中医口径症状表述 |
| 西医疾病 | `DiseaseWM` | ICD-11 第 1-24 章 |
| 西医症状 | `SymptomWM` | 现代医学症状 |
| 治法 | `TreatmentMethod` | 治疗法则 |
| 功效 | `Effect` | 功效术语（归一标准词表） |
| 化学成分 | `Component` | 二阶段加载，schema 预留 |
| 出处 | `Source` | 知识来源 |
| 分类 | `Category` | 树形分类导航节点 |

**实体公共基类** `EntityBase`：

```python
class EntityBase(BaseModel):
    model_config = ConfigDict(extra="forbid")  # 禁止未定义属性 → 防 schema 漂移
    LABEL: ClassVar[EntityType]
    provenance: Provenance  # 所有实体统一带溯源
```

`extra="forbid"` 是重点：如果有人往实体里塞了模型没定义过的字段，Pydantic 直接报错，防止数据结构悄悄"漂移"（Schema Drift）。

**两个安全相关字段**：

- `Herb.is_excluded_in_formula`（布尔）：L1 排除标记。毒性药材仍建节点（毒性知识是安全教育内容），但标记为"不得出现在任何方剂组成中"。
- `Formula.safety_level`（safe/caution）：由加载器按成分毒性**推导**，不手工填写。

### 4.3 关系（relations.py）—— 20 种边

关系模型比实体多一层约束：**定义域（起点）与值域（终点）校验**。

```python
class ComposedOf(RelationBase):
    RELATION_TYPE = "COMPOSED_OF"
    START_LABELS = frozenset({EntityType.FORMULA})   # 起点必须是 Formula
    END_LABELS = frozenset({EntityType.HERB})         # 终点必须是 Herb

    dose: float | None       # 折算后剂量（1钱≈3g / 1两≈30g）
    unit: DoseUnit | None
    raw_dose: str | None     # 古典单位原文，如"三两"
    role: FormulaRole | None # 君臣佐使
```

`RelationBase` 挂了一个 `model_validator`：构造时若起点/终点 label 不在允许集合内，直接抛 `ValueError`。这就是"语义严格原则"——从数据入口就挡住不合法关系，而不是等入库后才检查。

**完整关系清单**（`_RELATION_CLASSES`，19 个类；文档"20 种"的差异见下方说明）：

| 关系 | 边类型 | 语义 |
|---|---|---|
| ComposedOf | COMPOSED_OF | 方剂 → 药材（组成，含剂量/角色） |
| HasEffect | HAS_EFFECT | 药/方剂 → 功效 |
| TreatsPattern | TREATS_PATTERN | 药/方剂 → 证候（辨证核心链路） |
| TreatsDisease | TREATS_DISEASE | 药/方剂 → 中医疾病 |
| IndicatesMethod | INDICATES_METHOD | 方剂 → 治法 |
| HasSymptom | HAS_SYMPTOM | 证候/疾病 → 症状（含 is_primary） |
| AllaysSymptom | ALLAYS_SYMPTOM | 药/方剂 → 症状（缓解） |
| CorrespondsToDisease / CorrespondsToSymptom | CORRESPONDS_TO | 中西医疾病/症状映射 |
| ContraindicatedWith | CONTRAINDICATED_WITH | 药 → 药（十八反/十九畏） |
| PregnancyContra | PREGNANCY_CONTRA | 药 → Category「妊娠禁忌」 |
| SynergisticWith | SYNERGISTIC_WITH | 药 → 药（相须/相使） |
| Restrains | RESTRAINS | 药 → 药（相畏/相杀） |
| ProcessedFrom | PROCESSED_FROM | 炮制品 → 原药（如 熟地黄→地黄） |
| BelongsTo | BELONGS_TO | 实体 → Category（分类挂载） |
| FromSource | FROM_SOURCE | 实体 → Source（知识出处） |
| ContainedIn | CONTAINED_IN | 成分 → 药材 |
| Manifests | MANIFESTS | 西医疾病 → 西医症状 |
| AliasedIn | ALIASED_IN | 药/方剂 → Source（别名出处） |

> 关于"20 种"：设计文档将 `CORRESPONDS_TO` 记为两行（疾病映射/症状映射），代码里拆成两个类但共享同一 `RELATION_TYPE`；另有 `HAS_INGREDIENT_ROLE` 已弃用（并入 `COMPOSED_OF.role`）。因此实际生效的边类型是 18 种（+1 弃用）。

### 4.4 溯源（provenance.py）

```python
class Provenance(BaseModel):
    source_id: str       # 指向 Source 节点
    confidence: float    # 置信度 0-1
    extracted_at: datetime  # 入库时间 UTC
    method: ProvenanceMethod  # 获取方式
```

**置信度约定**（写死在 `ProvenanceMethod` 文档）：`curated=1.0`、`db_import=0.95`、`llm_extract`=模型自评（默认 0.7）、`manual_review` 最高优先。多源冲突时按 confidence 排序展示。

## 5. 数据管线：下载→解析→对齐→入库

管线是一串**离线批处理**命令，通过 CLI 串联（见 §9），把原始数据一步步变成图谱。

```
C1 下载 → C3 解析 → C6-C8 对齐 → C9 入库
(还有 C4 LLM 抽取、C10 向量索引，属可选/后续)
```

### 5.1 阶段 1：下载（download.py）

- 从 5 个数据源（§10）拉取原始文件到 `data/raw/<subdir>/`。
- 用 `manifest.jsonl` 登记每个文件的 `sha256`、`size_bytes`、`downloaded_at`。
- **幂等**：目标文件已存在且 sha256 与 manifest 一致 → 跳过（`--force` 强制重下）。
- 失败自动重试 3 次，指数退避；统一浏览器 User-Agent（部分站点拒绝非浏览器请求）。

**为什么登记 sha256**：既支持幂等重跑，又保留了数据来源与版本证据，供后续 `Source` 节点登记引用义务（版权合规）。

### 5.2 阶段 2：解析（parse.py + parsers/）

各源格式各异（xlsx/csv/pdf/txt），解析器负责把它们**归一**成统一 `envelope`：

```jsonl
{"kind": "entity", "label": "Herb", "record": {...}}
{"kind": "relation", "type": "COMPOSED_OF", "record": {...}}
{"kind": "quarantine", "record": {...}}
```

- 正常行写入 `data/parsed/<source_id>.jsonl`。
- 解析失败/校验不过的行写入 `<source_id>.quarantine.jsonl`（隔离清单，不进主流程）。
- 产出一个 `ParseStats`，含实体数/关系数/隔离数/**校验通过率**（valid / (valid+quarantined)）。

**PARSERS 映射**（6 个解析器）：`symmap`、`nmm`、`openkg`、`curated`、`batman`、`gbt15657`，各自对应一个解析器类。

### 5.3 阶段 3：对齐（align.py）

多源数据会出现"同名不同物"或"同物异名"，对齐就是判断哪些名称指同一个实体。

- **C6.1 候选池**：把 parsed 里所有实体的规范名+别名入池（按 label 分池）。
- **C6.2 召回**：用 bge-m3 把名字打成向量，算余弦相似度，取每个名字的 top-K 相似候选。
- **C7 精判**：对每个候选对判 `same`（同一实体）/`related`（相关但不同）/`different`（无关）。
  - 有 LLM 时走 `LLMJudge`（结构化输出判决+理由）；
  - 无 LLM 时走 `rule_judge`（规则降级）。
- **C8 审核队列**：`related` 或低置信对进 `review_queue.csv` 人工裁决；高置信 `same` 对进 `merge_candidates.jsonl` 供加载器消费。

**规则精判为何"安全优先"**（`rule_judge` 的核心，值得细读）：

它处理一个危险场景——中药短名里"近名不同药"极常见（赤芍/白芍、巴豆/巴豆霜、党参/明党参，语义相似度可达 0.8+）。纯靠相似度阈值判 `same` 会**危险合并**，而"巴豆/巴豆霜"恰好是 L1 生熟分界。所以规则判定顺序：

1. 归一化后字符相等 → `same`（跨源同名，主合并通道）
2. 仅差炮制词/部位词（制/炒/炙/生/熟/霜/粉 等）→ `related`（明确不自动合并）
3. 长名近似包含 → `same`
4. 编辑距离 + 语义双阈值 → `same`
5. 其余一律 `related`/`different` 进人工

**关键认知**：自动合并"宁缺毋滥"——宁可多留几个待人工审核，也不因误合并把"巴豆"和"巴豆霜"这种毒性不同的东西混为一个。

### 5.4 阶段 4：入库（load.py）—— 最关键文件的详细讲解

`load.py` 是管线核心，融合了**种子数据、垂直切片选择、L1/L2 安全过滤**。流程：

```
build_slice（三遍扫描精选 100 条候选） → apply_safety（L1+L2 过滤分级） → repo.load_envelopes（写库）
```

#### (1) 种子数据（SEED_*）

当前只入库 100 条（用户决策：先跑通全流程）。种子是硬编码的精选集合：

- `SEED_HERBS`：30 味药（含毒性药验证安全链路：附子、制川乌、半夏、甘遂等）
- `SEED_FORMULAS`：10 首经典方剂
- `SEED_PATTERNS` + `SEED_PATTERN_SYMPTOMS`：10 个证候及其主/次症（GB/T 16751.2 口径）
- `SEED_FORMULA_TREATS`：方剂→证候映射
- `SEED_FORMULA_COMPOSITIONS`：方剂组成兜底（parsed 缺失时）

#### (2) build_slice —— 三遍扫描

```python
第一遍：实体注册（Source + 种子名单四类）
第二遍：边收集（白名单语义，按 (start,type,end) 去重）
第三遍：端点补齐（被边引用但未注册的实体从 parsed 补全）
```

顺序固定，避免遍历间状态污染。最后做**终检**：边两端实体的 name 与 label 均已注册才对，label 不一致即丢弃（处理"跨源同名异标"，如 gbt15657 视"便秘"为病、symmap 视为症）。

#### (3) 源优先级（_SOURCE_PRIORITY）

```python
_SOURCE_PRIORITY = {
    "src-curator-v0": 0,   # 人工整理，最高
    "src-openkg": 1,
    "src-nmm": 2, "src-symmap": 2, "src-gbt15657": 2,
    "src-batman": 9,       # 组成混杂，最低
}
```

同名实体：小号源覆盖大号源；同级源做**字段级合并**（nmm 缺性味、symmap 补性味等互补）。这解决了"BATMAN 先注册污染 L2 判定"的问题（BATMAN 方剂元数据粗、组成混杂，必须被 openkg/curator 覆盖）。

## 6. 安全三层防线（L1/L2/L3 + E7）

这是项目最核心、用户最看重的设计。核心目标：**含毒性成分的方剂/药材，绝不给剂量，只给警示 + 引导就医**。

合规依据：**国务院令第 23 号《医疗用毒性药品管理办法》**、药典 2020【性味】【注意】项、GB/T 16751.2（主症/次症）。

### 防线总览

| 防线 | 作用于 | 位置 | 行为 |
|---|---|---|---|
| **L1 数据层过滤** | 入库前 | `load.py` | 含生品/无炮制形态管理品种的方剂**整体排除**，不入库 |
| **L2 风险分级** | 入库前 | `load.py` | 剩余方剂按成分毒性标 `safe`/`caution` |
| **L3 输出消毒** | 出图到用户 | `sanitizer.py` | caution 方剂/有毒药材 → 剂量掩码 + 标准警示 |
| **E7 兜底** | Agent 出口 | `graph.py` | 最终答案含毒性但缺警示 → 追加警示 |

### 6.1 L1：整方排除（`l1_strict_names` + `apply_safety`）

关键区分——**药典调剂规则**（国务院令第 23 号第九条）规定："处方未注明'生用'的毒性中药，应当付炮制品"。所以：

- 方剂组成写**规范名**（附子/川乌/半夏）→ 默认是炮制品 → **不触发 L1**（走 L2 分级）。
- 方剂组成写**"生"字头**（生附子/生川乌/生半夏）→ 触发 L1。
- **无炮制品变体**的管理品种（砒石/水银/斑蝥/蟾酥/雄黄…这些不存在"制XX"）→ 触发 L1。

```python
def l1_strict_names(toxic) -> set[str]:
    strict = set()
    for name, row in toxic.items():
        if row.get("l1_excluded") != "true":
            continue
        if name.startswith("生") or not (row.get("processed_variants") or "").strip():
            strict.add(name)
    return strict
```

在 `apply_safety` 中，若某方剂的 COMPOSED_OF 组成命中了 `strict_l1`，则该方剂**整体跳过**（实体 + 边都不入库），并写入 `exclusion_report.csv`（可审计）。

判断依据是 `data/curated/toxic_exclusion.csv`（50 行，每条含 `l1_excluded`、`processed_variants`、`toxicity_grade`、`basis` 字段）。

### 6.2 L2：风险分级（`apply_safety` 后半段）

对 L1 过滤后剩余的方剂：

```python
has_toxic = any(herb_toxicity.get(h) in (有毒, 大毒) for h in herbs)
is_batman = envelope["record"]["provenance"]["source_id"] == "src-batman"
safety = "caution" if (has_toxic or is_batman) else "safe"
```

两条规则：

1. 组成含"有毒/大毒"级药材 → `caution`（如四逆汤含附子）。
2. BATMAN 源方剂（组成不完整）→ 一律 `caution`（数据不完整，保守处理）。

**注意**：`SafetyLevel` 枚举里**没有 `high_risk`**——因为高危方剂在 L1 就已经被彻底排除，根本到不了 L2。这是"用数据层过滤替代高等级标记"的设计（ADR-013）。

### 6.3 L3：输出消毒（sanitizer.py）

这是"图谱 → 用户"的第一道出口。核心是两个函数：

**剂量隐藏矩阵**（`requires_mask`）：

| 对象 | 判定条件 | 处理 |
|---|---|---|
| 方剂 Formula | `safety_level == "caution"` | `usage` 掩码 + 组成剂量掩码 |
| 药材 Herb | `toxicity ∈ {有毒, 大毒}` 或 `is_excluded_in_formula` | `dose_range` 掩码 |
| 其余 | — | 正常展示 |

**标准警示文案**：

```
⚠ 该{方剂/药材}含毒性成分（{命中毒药材列表}）。出于安全考虑，此处不提供
剂量与用法信息。请前往正规医疗机构，由执业中医师辨证后开具处方使用。
```

**掩码占位符**：`【剂量信息已隐藏：含毒性成分，须由执业中医师开具】`

`sanitize_formula` 额外做一件事：遍历组成，把**有毒组成**的 `dose` 置空、`raw_dose` 覆盖为掩码，无毒组成（如干姜）剂量保留。这样"四逆汤"展示为「附子（君）【剂量已隐藏】/ 干姜 6g」。

**`sanitize_cypher_rows`（旁路防护）**：`run_cypher` 工具允许用户/LLM 写只读 Cypher 直接查图，可能绕过 get_herb/get_formula 的结构化消毒。所以对 Cypher 原始行输出再做兜底：行内若出现"有毒/大毒/caution"标记，则把该行的 dose/raw_dose/dose_range/usage 字段掩码。

### 6.4 E7 兜底（graph.py 的 `_e7_guard`）

```python
if MASK in text and "执业中医师" not in text:
    return text + "\n\n" + WARNING_TEMPLATE.format(...)
```

LLM 可能"自由发挥"，甚至把带掩码的内容重新组织后丢掉警示。E7 在 Agent 出口检查：最终答案含掩码（MASK）但缺"执业中医师"字样 → 强制追加标准警示。这是**双点掩码之外的第三道保险**。

### 6.5 追踪：查询「四逆汤」的完整链路

```
用户问「四逆汤的组成」
  → L1：四逆汤含"附子"（规范名，非生品）→ 不排除
  → L2：附子 toxic=有毒 → safety_level = caution
  → 入库：Formula 节点带 safety_level=caution
  → 查询：get_formula → sanitize_formula
       - usage 掩码
       - 附子 dose=None，raw_dose=【剂量已隐藏】
       - 干姜 dose=6g 保留
       - 附标准警示
  → API 层 /api/formula 再 sanitize 一次（双点掩码）
  → 返回给用户：含警示、无毒性剂量
```

## 7. Agent 层：六工具 + 双模式循环

文件：`agent/tools.py`、`agent/graph.py`。

### 7.1 六工具（AgentTools）

Agent 与图谱交互的唯一入口，全部返回经过消毒的结构化 dict：

| 工具 | 作用 | Cypher 特点 |
|---|---|---|
| `search_entities(name)` | 按名称/别名跨多标签检索 | 用 APOC 动态拼接 label |
| `get_herb(name)` | 药材详情 | OPTIONAL MATCH 功效 |
| `get_formula(name)` | 方剂详情+组成 | 组成/主治/疾病三段 OPTIONAL |
| `match_patterns(symptoms)` | 辨证 | **主症必配 + 次症加权** |
| `check_contraindications(herbs)` | 配伍禁忌 | 十八反 + 妊娠 + 毒性三查 |
| `run_cypher(query)` | 只读 Cypher 兜底 | 白名单 + 危险词扫描 |

#### 辨证工具（`match_patterns`，ADR-012）—— 重点

核心 Cypher：

```cypher
MATCH (p:Pattern)-[hs:HAS_SYMPTOM]->(st:SymptomTCM {name: s})
WITH p,
     sum(CASE WHEN hs.is_primary THEN 2 ELSE 1 END) AS score,
     ...
ORDER BY score DESC
```

**评分规则**：命中一个主症 +2 分，命中一个次症 +1 分，按总分降序返回 top-K，并带出"主症命中/次症命中"明细。

**为什么这样设计**（对照纯关键词匹配）：

- **主症必配**：主症是证候的核心（如"气虚证"的主症是乏力/气短/自汗），权重翻倍让它主导排序。
- **次症加权**：次症提供辅助证据，权重 1 分，避免"证候间区分度差"。
- **可解释**：返回 hit 明细，用户能看到"为什么判成这个证"。
- **确定性 + 零 token**：纯 Cypher 计算，不消耗 LLM token，结果稳定可复现。

#### 只读 Cypher 工具（`run_cypher`）—— 安全设计

```python
_READONLY_ALLOWED = ("MATCH", "RETURN", "WITH", "UNWIND", "OPTIONAL")
_FORBIDDEN_KEYWORDS = ("CREATE", "MERGE", "DELETE", "DETACH", "SET ", "REMOVE", "DROP", "LOAD CSV", "CALL", "FOREACH")
```

两层校验：

1. **白名单**：首子句必须是只读关键字（MATCH/RETURN/WITH/UNWIND/OPTIONAL）。
2. **危险词全串扫描**：即使 MATCH 开头，也可能携带 `DETACH DELETE`，所以全串扫描禁止写操作关键词。

目的：回退用 text2cypher 时，绝不能给 LLM 直接写库的能力（防注入 + 防误删）。

### 7.2 双模式循环（graph.py）

#### ToolLoopAgent（LLM 驱动）

```
system prompt + 工具清单
  → LLM 输出 JSON {"tool": name, "args": {...}} 或 {"answer": text}
  → 调工具 → 结果回填消息
  → 循环（最多 MAX_STEPS=8）
  → 产出最终答案 → E7 兜底
```

- `SYSTEM_PROMPT` 明确要求：优先调工具、带 `_safety_warning` 必须原样复述、不编造、结果够了就停。
- `TOOL_SPECS` 是给 LLM 看的六工具说明（name/description/parameters）。
- `ChatLLM` 是 Protocol（只要实现 `chat` 方法即可注入），测试用 `FakeChatLLM`。

#### RuleBasedAgent（无 LLM 降级）

当 LLM 未配置（`build_llm_from_settings()` 抛异常）时，自动降级为规则 Agent。它用**关键词路由** + **模板化输出**：

```
"辨证/什么证" → match_patterns
"禁忌/相反/配伍/一起用/同用" → check_contraindications
"方/汤/散/丸" → get_formula
"药/草" → get_herb
否则 → search_entities
```

规则 Agent 的意义：**离线即可跑的垂直切片全流程验证**，不依赖 LLM 也能演示安全链路（毒性隐藏、辨证、禁忌）。

> 说明：当前 RuleBasedAgent 是"命中第一个路由即返回"的单意图实现。若需支持多意图（用户同时问"附子有毒吗，和甘草能同用吗"），需改为"收集全部命中路由 → 顺序执行 → 合并答案"，这是已识别但未实现的优化点。

### 7.3 降级链总览

```
ToolLoopAgent（LLM） ── 无 LLM 配置 → RuleBasedAgent（规则）
       │
       └── 出口统一过 E7 兜底 + L3 sanitize
```

### 8.2 双点掩码（F3 序列化掩码）

这是 API 层最重要的设计点。工具层已经消毒过了，但 API 出口**再消毒一次**：

```python
@app.get("/api/herb/{name}")
async def herb_detail(name: str):
    detail = tools.get_herb(name)   # 第一道（工具层已 sanitize）
    ...
    return sanitize_herb(detail)    # 第二道（API 层再 sanitize）
```

**为什么双点**：即使工具层将来漏了消毒，API 出口这层也能兜住剂量不泄露。属于"纵深防御"（Defense in Depth）思想，与 L3+E7 一起构成多重保险。
